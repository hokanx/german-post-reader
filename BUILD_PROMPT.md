## motion (framer-motion) — kits ship with animation, never dead-static

a less-generic look still feels generic if nothing moves. every kit gets a real motion layer. it is NOT optional garnish — it is part of the quality bar, same as contrast and focus rings.

1. **install it**: from inside `project/`, `npm install framer-motion`. (app-router: mark animated components `'use client'`.)
2. **define the system once**, in `design-system/MASTER.md` under a "motion" heading — then reuse it everywhere instead of hand-tuning per component:
   - **durations**: fast `0.15s` (hover/tap), base `0.25s` (entrances), slow `0.4s` (hero / route). nothing in the UI animates longer than `0.4s`.
   - **easing**: ease-out for entrances (e.g. `[0.22, 1, 0.36, 1]`), ease-in-out for state changes. no linear, no bouncy springs unless the direction is explicitly playful.
   - **standard variants**: `fadeRise` (opacity 0→1, y 12→0), `stagger` (parent staggers children ~0.06s), `hoverLift` (scale 1.02 + shadow), `tap` (scale 0.98).
3. **apply it where it earns attention**:
   - **section/hero entrances** on scroll: `whileInView` with `viewport={{ once: true, margin: '-80px' }}` + `fadeRise`. once, not on every scroll-by.
   - **lists / card grids**: `stagger` the children so they cascade in.
   - **interactive cards + buttons**: `whileHover={hoverLift}` + `whileTap={tap}`. subtle — this is feedback, not a trampoline.
   - **modals / sheets / dropdowns / route changes**: enter+exit via `AnimatePresence`. never pop in/out instantly.
4. **accessibility is mandatory**: call `useReducedMotion()`; when true, drop transforms/translation and keep opacity-only (or no) animation. never animate something that shifts layout after paint (guards CLS).
5. **intensity matches the locked design direction** (from SPEC.md, if present): restrained + precise for minimal / editorial / premium-dark; livelier and springier for playful / bold. when no direction is set, default to restrained.
6. **motion slop to avoid**: infinite looping background animations (unless the direction calls for it), animating every tiny element, parallax that fights scroll, durations over `0.4s` on UI affordances, anything that delays the user seeing content.

## design discipline (design phase, not brainstorming)

before writing code in any step:

- **read SPEC.md first**. SPEC.md is the contract. your design must implement what SPEC.md describes — no more, no less. if a step seems to ask for something SPEC.md doesn't cover, treat that as a SPEC.md gap to flag (not a license to expand scope).
- **design from SPEC.md, not from a blank page**. write the implementation-level design to `docs/superpowers/specs/<topic>.md` — this is the HOW that fills in details SPEC.md couldn't (file layout, error handling, edge cases, redirect targets). do NOT invoke `superpowers:brainstorming` to re-ask the user the user-facing questions SPEC.md already answered.
- **when ambiguity is real**: if SPEC.md is genuinely silent on a load-bearing decision (e.g. "auth works" but doesn't say magic-link vs password — and the answer changes the code materially), THEN you may briefly ask the user one tightly-scoped question. otherwise, pick a sensible default consistent with the spec and proceed.
- **assess scope before details**. if the step description bundles multiple independent subsystems ("auth + storage + billing"), flag it and decompose first. don't burn time refining details of something that needs to be broken up.
- **propose 2-3 approaches** when the right path isn't obvious. lead with your recommendation and explain why. don't just announce a choice — show the alternatives you didn't pick.
- **design for isolation and clarity**. each new file should have one clear responsibility. you should be able to say in one sentence: what it does, how to use it, what it depends on. if you can't, the boundaries are wrong.
- **smaller, focused files over large ones**. you reason best about code you can hold in context at once; edits are more reliable when files are focused. when a file grows large during a step, that's a signal it's doing too much.
- **YAGNI ruthlessly**. don't add features the spec didn't ask for. don't add error handling for cases that can't happen. don't add abstractions for hypothetical future requirements.

## task discipline (writing-plans phase)

### file structure first

before writing tasks, list which files get created or modified and what each is responsible for. this locks in decomposition decisions. files that change together live together; split by responsibility, not technical layer. in existing codebases, follow established patterns — don't unilaterally restructure unless a file you're already touching has grown unwieldy.

### bite-sized sub-steps

inside any step you execute, treat sub-steps as 2-5 minute actions:

- "write the failing test" — sub-step
- "run it to confirm it fails as expected" — sub-step
- "implement the minimal code to make it pass" — sub-step
- "run the tests and read the output" — sub-step
- "commit with a message that names what shipped" — sub-step

never write a sub-step as a vague verb without a target. "add validation" is not a sub-step — "add a zod check that `projectSlug` matches `/^[a-z0-9-]+$/` in `apps/web/src/lib/schemas.ts`" is a sub-step.

### no placeholders (these are plan failures — never)

- "TBD", "TODO", "implement later", "fill in details"
- "add appropriate error handling" / "add validation" / "handle edge cases"
- "write tests for the above" without the actual test code
- "similar to step N" — repeat the code; sub-steps may be read out of order
- steps that describe what to do without showing how — code steps need code blocks
- references to types, functions, or methods not defined anywhere

### plan self-review (run BEFORE executing)

after writing a plan, check it against the spec with fresh eyes:

1. **spec coverage** — skim each requirement in the spec. can you point to a sub-step that implements it? list any gaps; add sub-steps for them.
2. **placeholder scan** — search the plan for any "no placeholders" red flags above. fix them.
3. **type consistency** — do the types, signatures, and property names in later sub-steps match what earlier sub-steps defined? `clearLayers()` in step 3 but `clearFullLayers()` in step 7 is a bug — caught here.

fix issues inline and move on. no need to re-review.
